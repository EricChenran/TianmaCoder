# Web GUI 黑盒测试

用 `browser_*` 工具族（navigate、snapshot、aria、elementInfo、screenshot、click、hover、
fill、check、type、press、select、scroll、wait、viewport、dialog、downloads、record、tabs、
getState）像真人一样操作页面，把"动作 → 观察"的循环走完，最后交出一份**每个测试点都带截图证据**的报告。

## 五条硬性原则

1. **纯 GUI 黑盒**：只操作页面上可见、可点的元素。允许截图与只读 DOM 观察；**禁止用任何方式注入 JS
   去改页面状态、触发交互或绕过前端逻辑**。工具族本身也没有 `evaluate`，不要绕开它去用别的浏览器做这件事。
2. **忠于页面实际行为**：所有结论必须来自页面真实表现，不猜测、不推测。正常 GUI 操作失败就停下记录，
   **不要用替代手段强行推进**。
3. **测试与修复分离**：测试期间不改被测代码。某条路径被缺陷挡住就记录、跳过，继续测不受影响的点；
   只有测试明确结束、且用户要求改代码时才动修复。
4. **双证据交叉核对**：结论必须同时有只读 DOM 核对与截图目视，二者互为佐证、不能互相替代。一个测试点
   若没有至少一张**真正看过的**截图作为证据（工具直接返回的图，或读过的截图文件），视为未完成——
   **没看过图就不算观察，没看过图不得判定通过或失败**。
5. **遵循工具自身规则**：本技能只定义测试方法；当它与浏览器工具族的规则冲突时，**工具规则优先**。

## 工具族操作纪律

以下纪律来自实战中反复出现的失败模式，务必遵守。

### 定位

- **以 `browser_snapshot` 的 ref 为准**（e1、e2…）。快照给出的 role/name 是页面事实，照着它定位，
  **不猜 selector、不猜标签文字、不猜 URL 形态**。
- `browser_aria` 的 ref **不能用于点击**：点击缓存只认 `browser_snapshot` 写入的 ref，而两个工具的编号
  长得一样（都是 e1/e2…），混用会报 stale/unknown。要动元素就先做一次 `browser_snapshot`。
- 同一个选择器或 ref **失败后不要原样重试**。先重新观察（重取 `browser_snapshot`，必要时再截图）确认
  真实状态，再判断是页面缺陷（元素确实不在）还是定位失效（按新事实重建定位）。
- **ref 会失效**：导航、页面重渲染、窗口尺寸或侧栏几何变化之后，旧 ref 指向的坐标已经陈旧，必须重新
  snapshot 再用，否则会静默点空。用选择器定位的动作是实时探测的，对此免疫。

### 动作

- **一个观察周期只做一个状态变更动作**，然后观察，再决定下一步。
- **按期望效果判定成败**，不要只看工具的回报文本。回报 "Clicked … at x, y" 只说明投递了坐标，不代表命中；
  URL 没变也不代表点击失败，要看页面是否出现预期变化。
- 弹出新页面时，同时列受控标签与人已打开的标签（`browser_tabs` 的 `list` 与 `listUserTabs`），按 url/title
  认领（`claim`），**不要按数组位置选**，也不要另开一个同 URL 的重复页。每批操作前先列一次标签，
  不要凭记忆认定当前页面。

### 观察

- 默认用 `browser_snapshot` / `browser_elementInfo` 读页面；**不要默认"快照 + 截图"一起取**
  （每次截图都是图像 token）。只在真正需要视觉判断时才截图：要看版式/样式/渲染、用户要求截图或视觉验证、
  或目标不在 DOM 快照里（canvas、自绘控件）需要瞄坐标。
- **每次截图都要真的看**；只看工具回报不看图，不算视觉验证。
- **瞬时态**（toast、tooltip、loading、动画）必须在同一轮里连续完成：先截"动作前"的图 → 执行动作 →
  等目标状态出现（优先 `browser_wait` 等具体元素，别用固定死等）→ 截"动作后"的图，然后再看图。
  普通静态页面不需要这种前后连拍，一次常规截图即可，但**图仍然必须看**。
- **区分 DOM 级与渲染级命令**：`navigate`、`getState`、`snapshot`、`aria`、`elementInfo`、`fill` 是 DOM 级的，
  窗格不可见时仍然可用；`screenshot` 与坐标类动作（坐标 `click`/`hover`、`cuaScroll`、`cuaDrag`）依赖真正在
  呈现的表面，窗格被收起或切到别的会话时会**静默失真**——工具回报成功，页面其实没动静。判定"页面到底在不在
  呈现"，用 `browser_elementInfo` 查 `html` 的 box 与 visible，**别只看截图**（此时截图可能是一张 1×1 的空白图）。
- 坐标只用于 canvas、自绘控件或快照里没有的视觉目标，且必须配截图瞄准。为了绕过失败的定位而改用坐标、
  Tab 键或快捷键，属于违规。

### 证据与归档

- 在建的测试目录下建一个专用文件夹（如 `gui-test-screenshots/`），把每张截图的副本按测试点编号命名
  （`t1_before.png`、`t1_after.png`…），供报告逐点引用。
- 报告要求：哪些测试点通过、哪些失败（含复现步骤与截图）、哪些被阻塞未能执行、收集到的控制台报错或页面上
  可见的错误表现。**每个测试点（无论通过还是失败）都要引用对应截图的绝对路径**作为证据，不要把截图全堆在
  报告末尾，也不要只给纯路径不给图。

## 四个阶段

### 一、场景评估与测试计划

- **信息完整**（用户给了明确步骤与预期结果）：跳过计划，直接进入后续阶段。
- **信息部分**（给了功能描述、缺陷描述或需求文档）：轻量计划——明确要验证什么/复现什么、通过标准是什么，
  然后直接做，不要请求确认。
- **信息不足**（只给了一个 URL 或一句"你测一下"）：完整计划——先打开页面截图看全貌，识别页面类型
  （表单页/列表页/详情页/看板）与核心交互元素，再按优先级组织测试点：
  - **P0 主流程**：核心功能的正常路径（提交表单、完成搜索、切换页签）。
  - **P1 交互反馈**：动作后的反馈是否正确——loading、成功/失败提示、禁用态、跳转。
  - **P2 输入边界**：空输入、超长输入、特殊字符、重复提交。
  - **P3 版式与样式**：元素重叠、文字溢出、对齐一致性、观感问题。

  把计划给用户看，然后**立即从 P0 开始，不要等确认**。
  **例外**：页面需要登录凭证，或测试会写入真实数据（下单、支付、删除），先停下问用户。

### 二、测试环境准备（需要时）

正式测试开始前，可以用任何必要手段准备环境，黑盒限制在这一阶段不适用：启动/重启开发服务器与依赖服务、
改配置文件、准备测试文件、初始化或灌入测试数据、创建测试账号、按工具支持的方式预置登录态（预置
cookie/storage，或用测试账号走 GUI 登录，或按工具规则复用人已登录的标签页）。

约束：

1. **准备与测试明确分界**：准备完成后明确声明"环境准备完成，开始正式测试"，此后黑盒约束立即生效，
   不得再做有副作用的注入。
2. **准备不能代替被测行为**：准备只能让被测功能"可达"，不得预先触发或完成被测功能本身（例如测下单流程时，
   不要在准备阶段直接往库里插一条订单）。
3. **不得回退到准备阶段绕过失败**：正式测试中若发现环境问题，先声明当前测试点无效，回到本阶段重新准备，
   再从该测试点头开始，并在报告中如实说明。
4. **记录所有准备动作**，让用户能区分"预置状态"与"测试自身产生的状态"。

### 三、执行：动作 → 观察 → 动作

- 一次只做一个状态变更动作，随后观察，再决定下一步。
- 元素定位失败：不要原样重试，按"定位"纪律重新观察并重建定位。
- 页面加载失败（超时、白屏、报错）：截图记录当前状态，作为问题上报，并跳过后继依赖该页的测试点。
- 工具不支持的操作（如文件上传）：该测试点记为"运行时不支持"并跳过，**绝不伪造成功，也不要靠注入绕过**。
- 响应式/多尺寸测试：只在测试点明确要求时用 `browser_viewport` 调整尺寸，测完恢复原尺寸，
  **不得用它来逃避失败状态**。
- 想重开一个测试点时，回到入口页重置状态是允许的；但不得用刷新、前进/后退、改尺寸来逃出当前失败状态。

### 四、输出结论

按记录的观察汇总：通过哪些、失败哪些（复现步骤 + 截图）、哪些被阻塞未执行、收集到的控制台错误或页面上
可见的错误表现。每个测试点都要引用对应截图的绝对路径。

报告格式：用户指定了格式/文件/语言就严格照做；没指定就默认输出**图文交错的 Markdown 报告**，用标准
Markdown 图片语法就地引用截图（如 `![登录页截图](file:///绝对路径/login.png)`），不要只给纯文本路径，
也不要把所有截图攒到最后。

## 环境限制（必须如实告知用户）

- 依赖真实呈现表面的命令（截图与坐标类动作）在窗格不可见时会静默失真，此时**以 DOM 级判读为准**，
  并把"视觉未验证"如实写进报告，不要因为拿到一张 1×1 的图就宣称通过。
- 若当前运行环境无法启动桌面浏览器（例如受限沙箱禁用了渲染进程所需的 IPC），涉及桌面端自身的 GUI 验证
  应交给用户在其终端执行，不要伪称已验证。
