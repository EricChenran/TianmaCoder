# Agent Note: 部门模式以提示词节注入规则

Status: implemented

[English](2026-09-23-department-modes.md) | 中文

## Problem

产品在通用编码模式之外还要交付两个固定团队模式：技术部（后端、前端、运维三类工程纪律）与商务部（需求文档、报价单、案例检索）。两套规则最初都是 ZCode 技能文档：`skills/` 树里的 markdown，按会话发现、按需读取为工具结果。

这个形态与"模式"不相容。模式的规则必须在该模式的每个会话的每一轮都在场、在其他任何模式都不存在，并且不能被当作文档寻址——会话可以打开它、引用它、复制它。商务部的流程还额外需要自己的文档生成脚本，而技能会把这些脚本作为文件放进会话可读的目录。

## Decision

一个包 `@tianma/dsh-department-prompts` 以编译内置文本承载两套规则，并把所选部门的规则注册为单条字面 system-prompt 节：`tianma:department`，节序 `150`，排在 Tianma 行为准则之后、计划策略之前，`interpolate: false` 使规则引用的 JSON 示例保持字面量。`@deepseek-ai/dsh-web-app` 组合包里随发行版交付的 `tech` 与 `business` 预设重述 `standard` 的插件清单并增加一行选择部门，因此一种模式与 `standard` 的差别只在于模型读到的规则。

商务部工具箱作为包资源交付，挂载时发布到 `<harness home>/department/business-tools`。该目录只以受管变量 `DSH_DEPARTMENT_TOOLS` 到达模型的 shell 调用（经 `ctx.shellEnv` 注册），因此规则文本、日志与命令都不出现该路径；发布与注册都经 `ctx.effect` 随插件 fiber 回退。

两套规则都已适配本 harness 的工具：技能调用、`<本技能目录>` 脚本路径、浏览器自动化步骤与 ZCode 的文件引用指令全部移除；商务规则改为通过工具箱变量调用已发布脚本、转换后校验 PDF 确实生成，并在本机没有 Word 时退到 harness 的 Office 转换。案例检索改写为 `web_search`/`web_fetch` 流程，并如实写明自身局限，取代原文档针对 modao.cc 的 DOM 手工打法。

规则文本以明文提交进本仓库，这一点由所有者明确接受：两个模式必须随产品交付，而任何进入系统提示词的文本无论以何种形式存放，都可以从打包后的应用中提取出来。

## Alternatives considered

**把规则作为技能交付。** 发现是按会话进行的，文本变成会话可以打开和引用的文档，而且部门的规则会出现在每个模式的技能目录里——正好是模式必须反转的两个性质。

**把规则放进配置。** 配置字符串又变成可读文件（在 profile patch 里），而且对所有模式是同一份，无法按模式选择。

**把工具箱脚本留在用户工作区。** 规则会依赖一个用户可移动、可删除的目录，脚本也会落在模型会读取的项目里。

**运行时从文件加载规则文本。** 规则变成一条路径：一个可打开的文件，以及多一处能被读者找到文本的地方。

**用构建期密钥加密存储文本。** 密钥与解密代码同包交付，只是提高了读文本的成本、并不能使其不可达，同时让规则无法在仓库里 review。

## Consequences

- 选择技术部会增加约 6,400 token 的系统提示词，商务部约 2,700，每请求一次；未被选择的模式不产生开销。
- 两条节都位于稳定的系统提示词前缀内，对 KV 复用的影响与其他静态节相同。
- `apps/cli/tests/web-agent-presets.e2e.ts` 启动随发行版的组合，钉住六个预设的名录、每个部门的节标题，以及工具箱变量与它下面发布的文件。
- 工具箱面向 Windows：`to_pdf.py` 通过 COM 驱动 Word，`open_folder.py` 调起桌面外壳。
- 文案调整属于改包而非改配置；各模式的契约与边界由包 README 负责。
